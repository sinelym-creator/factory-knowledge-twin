# T2-5 — WO 초안 생성·승인 API

## 목표

계약의 work-orders 표면(`GET/PATCH /work-orders/{woId}` · `POST …/approve|reject`)을 501에서 해제한다 — **「화면 ④의 지울 수 없는 항목」을 UI가 아니라 서버가 강제**(원장 요지 · R12 REQUIRES). 초안 생성은 T2-3 산출(draft_work_order)이 이미 담당 — 본 티켓은 «펴기·편집·승인/반려»다.

## 단계 게이트 (순서 고정 — 초안 · 발주 시 확정)

1. **계약·정본 실독 보고 선행** — work-orders 계약 3행 + 스펙 §4(work_order · 「전체 행 + 승인 이력」) + T2-3 착지 store(workOrderDraft) 실독 → 🔴 판정 회부 2건이 핵심: ⓐ **WO·승인 이력의 저장 축** — 스펙 §4 「승인 이력 테이블」(DB 마이그레이션 009) vs 세션 스코프 store(J-3 「SSOT 쓰기 0」 계열 — run 부산물과 같은 성질인가, 공장 사실인가) ⓑ **`approval_state` 전이 규칙 확정**(스펙 부재 — Q-11 · 오케 성문 몫: 후보 = draft→approved|rejected · 재편집 허용 여부 · 전이 위반 = 명시 오류).
2. **읽기·편집** — draft 펴기(evidenceIds 포함 전문) · PATCH 부분 갱신. 🔴 Q-27 재확인 의무 발동 지점: replay run의 workOrderDraft 본문은 이벤트 밖 — replay run에 대한 WO 조회가 «조용한 빈 값»이 되지 않게 명시 응답 설계(J-G 계열).
3. **R12 서버측 강제** — 안전 조치(REQUIRES 유래 — SAF-LOTO-01 등) 항목은 PATCH로 «삭제 불가»: 시도 = 명시 거절(계약 오류 형상 · 사유 코드) · 서버가 강제하고 UI는 그리기만 한다. 🔴 대조군 필수: 안전 조치 삭제 시도 → 거절 · 일반 항목 삭제 → 성공.
4. **approve/reject** — `{status, auditId}` 응답 · 이력 기록(저장 축 = 게이트 1 판정분) · 전이 규칙 위반 = 명시 오류.

## AC (초안 — 발주 시 확정)

- [ ] 계약 표면 green · 계약 밖 경로 0 · 응답 형상 = 계약(서술 미정 자리는 게이트 1 회부 — v0.1.x append는 오케).
- [ ] 🔴 R12 강제 실물: REQUIRES 유래 안전 조치 삭제 시도 = 명시 거절(E1) + 일반 항목 대조군 · 우회 경로(PATCH 전체 치환 등) 성문 점검 — 「형제를 먼저 센다」.
- [ ] approve/reject 전이 규칙(게이트 1 확정분) 준수 · 위반 = 명시 오류 · auditId 실물 + 이력 조회 가능(축은 판정분).
- [ ] Q-27 지점: replay run WO 조회의 명시 응답(조용한 빈 값 = FAIL).
