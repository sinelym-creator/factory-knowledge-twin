# T2-4 — structured audit event + replay fixture 녹화

## 목표

조사 실행 스트림(agent-events · seq 기준)을 **커밋된 replay fixture**로 굳힌다 — Phase 3 replay engine·Phase 4 fallback의 원천(원장 요지). T2-3의 「정직한 대가」(프로세스 재기동 시 run 소실 — J-3 성문)를 fixture 축이 메운다: 내구 경로 = 세션 저장소가 아니라 **커밋된 재생본**이다.

## 단계 게이트 (순서 고정 — 초안 · 발주 시 확정)

1. **계약·판정 실독 보고 선행** — `mode` 낱말 v0.1.3(실행 = live · fixture 재생 = replay · «지금 501이 참»인 replay 요청이 이 티켓에서 «참 200»이 된다) + agent-events 스키마 + T2-3 착지 구조(store·events) 실독 → fixture «형식·저장 위치·녹화 대상 run 선정»을 보고로 올리고 판정 받는다(🔴 fixture는 리포에 커밋되는 실물 — 공개 경계 심사 대상: synthetic 데이터만·자격 증명 0·절대경로 0).
2. **녹화** — GS-01 실행 1회의 이벤트 스트림(seq 전열)을 fixture로 저장. 🔴 녹화본은 «가공 없이» 실행 산출 그대로(ts·seq 재조립 금지 — T2-3 자기 정정 ①의 교훈: 재조립은 조용히 가른다).
3. **재생** — `mode:"replay"` 요청이 fixture를 재생: 같은 seq 열 · envelope `mode:"replay"` 표기 · WS·GET /events 동일 원천. 실행 경로와 재생 경로가 «한 이벤트 저장 형식»을 공유(이원화 금지).
4. **재생 정직성** — replay run은 «새 조사가 아님»이 표면에 드러난다(mode 표기 · 이벤트 원문 보존). 🔴 fixture 없는 시나리오의 replay 요청 = 여전히 명시 오류(조용한 빈 재생 금지).
