## 2. 축② — 대조군이 「같은 무대 前→後 한 변수」인가

**성립한다.** YAML step 순서 실측:

```
run ai-api (컨테이너 기동)      ← 무대는 여기서 한 번만 뜬다
대조군 — 색인 0 에서 스모크      ← 前
build index (계수 stdout)       ← 변수는 이것 하나
index counts (DB 직접 질의)
benchmark smoke (색인 후)        ← 後
```

- 「만든 뒤 지운」 순서가 아니라 **만들기 «전»에 잰** 순서다(발주 ②의 물음).
- 두 열 사이에 **컨테이너 재기동·재생성이 없다** — 같은 인스턴스가 두 열을 다 받았다.
- 대조군은 자기 전제를 스스로 확증한다: `chunks = 0` 이 아니면 `exit 1`(「색인 전인데 chunk N행 — 대조군이 성립하지 않는다」).
- 실패를 삼키지 않는 형태: `set -uo pipefail` + `node ... || rc=$?` ✔.
- **무대가 처방을 실었는가**: `/api/health` 응답의 `build` = **`9125e20a3dcc…`** = 1차 run 의 PR 커밋 → 그 컨테이너가 이 PR 의 코드다(자기 신고지만 sha 는 대조 가능).

## 7. 회부 1건 — **해소 확증**(1 판 = 미해결 · 2 판 = 닫힘, 잔여는 이름으로)

**1 판에 적은 회부**: 대조군 step 이 `--out` 없이 돌아 前 열에 요청별 `status` 가 없다 → 「hit 0」이 **200 위**인지 **비200 위**인지 못 가른다.

**소조각이 그 축을 세웠고, 답은 내가 예상한 갈래가 아니었다.**

| | 1 판(회부 시점) | 2 판(해소 뒤) |
|---|---|---|
| 前 열 status | **관측 없음** | **503 × 20**(200 = 0건) |
| 그 503 의 이름 | — | **`index_unavailable`**(원문 확보 = E1) |
| hit 총합 | 0(문면만) | **0**(계수 재확인) |
| 빨강의 주어 | 「색인 없음」으로 **추정** | 서버가 **이름으로 말함** → 귀속 확정 |

- 🔴 **회부의 값은 내 가설이 맞아서가 아니라 «가를 수단»을 세웠기 때문에 생겼다.** 나는 「200 위의 hit 0」일 것이라 보았고, 실측은 **503 일관**이었다. 수단이 없었으면 그 틀린 문장이 그대로 판정문에 실렸을 것이다.
- 🔴 **중간에 한 번 더 갈린 자리 — 「code 가 없다」가 아니라 「안 봤다」였다.** 두 dispatch 동안 `codes` 집합이 빈 채였다. 원인은 본문 부재가 아니라 **봉투 정본을 안 본 것**이다: 이 서비스의 오류 봉투는 `{"error":{"code","message"}}` 인데(계약 `packages/contracts/rest-api-v0.1.md:11` + 구현 `app/errors.py:249 _contract_error` 가 `ErrorResponse(error=ErrorBody(...))` 로 FastAPI 기본 `detail` 을 갈아엎는다) 프로브는 top-level `code` 와 `detail.code` 만 읽었다. 나는 이 진단을 원문이 나오기 «전»에 코드 축에서 내고 **예측 둘을 선언**했다 — ① 원문엔 `error.code` 가 실재할 것 ② 그래도 `codes` 집합은 빈 채일 것. **둘 다 적중**했고, 그 뒤 정본 경로 한 줄로 `codes=['index_unavailable']` 이 섰다. (예측 선언 = 이 진단의 대조군이다.)

### 남은 잔여 — 값이 아니라 이름으로

- 🔴 **ⓑ 「같은 조건 재현 관측」이지 「그 실행의 관측」이 아니다.** 프로브는 대조군 스모크 **다음 별 step**(YAML 176행 · `build index` 183행 앞)이라 **exit 5 를 낸 호출과 다른 라운드**다. 같은 무대·같은 국면(chunk 0 · 컨테이너 재기동 0)이지만 **원 호출의 봉투 자체는 여전히 미관측**이다.
- 그 자리를 닫는 것이 **O-54 ⓐ**(러너 `--out` 을 exit 5 가드 «앞»으로 — 현 러너는 118행 exit 5 가 172행 쓰기보다 앞줄이라 이 국면에서 파일을 안 만든다). 그때 원 호출 봉투를 직접 보게 되므로 두 번째 계측기의 존치 여부도 그 뒤에 판단한다.

3. §1-c 의 C 열은 스크립트의 `topk` 를 원시로 썼지만, `topk` 자체는 여전히 **대상이 만든 문자열**이다. 「검색이 실제로 그 문서를 돌려줬는가」를 API 응답 원본까지 거슬러 확인한 것은 아니다.
4. **1 판의 §4 에 「변경 파일 1본뿐」이라 적었다.** 그 시점(head `0a3cac3`)에는 참이었으나 소조각이 프로브를 더해 **2본**이 됐다 — 판정문의 시점이 병합 sha 보다 먼저 늙는 자리다. 2 판에서 병합 실물로 재판독해 정정했다(발주의 전제가 그 사이에 죽는 자리의 재발 · 앞 §8-2 와 같은 병).
5. §1-a 의 「내가 판정한 두 run 의 前 열도 503」은 **추정(E2)**이다. 코드 무변경 + build sha 일치가 뒷받침하지만 그 run 을 찍은 값은 아니다 — E1 로 올려 적지 않았다.
