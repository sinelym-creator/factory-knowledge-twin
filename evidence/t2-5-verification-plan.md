## 1. 축별 계획 — 「무엇이 빨강이면 결함인가」

### 축① 전이 규칙 전수 (계약 v0.1.4 · ⓑ)

정본이 정한 것: `pending → approved | rejected` **인접 전진 2쌍만** · approved/rejected =
**종단** · **PATCH 는 pending 에서만**.

🔴 **「전 조합」을 조합으로 센다** — 합법만 확인하고 「나머지는 알아서 막히겠지」로 두지 않는다.
상태 3종의 순서쌍 9칸 + PATCH 3칸 = **12칸 전수**.

| 출발 → 목표 | approve | reject | PATCH |
|---|---|---|---|
| `pending` | 합법 | 합법 | 합법 |
| `approved` | 위반(재승인) | 위반(번복) | 위반(종단 편집) |
| `rejected` | 위반(번복) | 위반(재거절) | 위반(종단 편집) |

| red 조건 |
|---|
| 합법 3칸 중 하나라도 거절 |
| 위반 9칸 중 하나라도 **성공**(200) — 「스펙이 침묵한 건너뜀도 위반」(E-7 선례) |
| 위반이 막히되 **사유 코드가 합쳐져** 있다 — 「종단 상태다」와 「그런 전이는 없다」는 다른 사건 |
| 종단 상태에서 PATCH 가 «조용히 무시»되고 200 을 준다 — 거절이 아니라 침묵이면 red(V-6 계보) |

### 축② R12 서버측 강제 — 성문 형제 6종 + 대조군

정본: 편집은 **화이트리스트**(허용 열거)다 — 「막을 목록은 형제가 계속 생긴다」.

| # | 형제 | red 조건 |
|---|---|---|
| 1 | `safetyMeasures: []` | 200 이면 red |
| 2 | 부분 삭제(일부만 남김) | 200 이면 red |
| 3 | mandatory 무력화(항목은 두고 속성만) | 200 이면 red |
| 4 | SOP 근거 삭제(뿌리 자르기) | 200 이면 red |
| 5 | 전체 치환 | 200 이면 red |
| 6 | 키 누락 = 무변 | 키가 없는데 **값이 바뀌면** red |
| **대조군** | 일반 항목(제목·일정 등) 삭제·수정 | **성공해야** 한다 — 🔴 전부 거절이면 「R12 를 지킨」 게 아니라 **편집을 막은** 것이다 |

🔴 **거절의 «모양»도 잰다.** 6종이 전부 같은 코드로 막히면 화면은 왜 막혔는지 말할 수 없다.
사유가 갈리는지 본다(계약 오류 형상 안에서).

### 축③ 🔴 7번째 형제 탐색 — 성문 6종 «밖»

**방법(착수 전에 못박아 둔다).** 6종을 더 들여다봐서 나오지 않는다. 목록이 **어떤 질문에서
만들어졌는지**를 되짚어 축으로 분해하고, 그 축의 «빈칸»을 센다.

| 축 | 6종이 채운 칸 | 🔴 빈칸(내 탐색 후보) |
|---|---|---|
| 연산 | 제거 · 부분제거 · 치환 · 속성변경 · 무언급 | 타입 위반 — `null` · 문자열 · 객체 |
| 필드 | 직접(`safetyMeasures`) · 간접(SOP 근거) | 화이트리스트 «밖» 필드 경유(`note`·`gaps` 로 옮기고 원본 제거) |
| 경로 | `PATCH` | `approve`/`reject` 요청 **본문**으로 편집 |
| 동일성 | — (아무도 안 물었다) | 표기 변형으로 «다른 항목»처럼 보내 원본을 밀어내기 — 🔴 **V-1 계보**(대소문자·앞뒤 공백·유니코드 정규화) |

🔴 **판정 규율**: 위 넷은 **후보**다. 던져 보고 통과하면 형제, 막히면 「막힌다」로 적는다.
**못 찾으면 「못 찾았다」고 쓴다** — 없는 것을 지어내 형제라 부르지 않는다.
