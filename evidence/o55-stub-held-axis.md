## 1. 🔴 발주의 전제 하나가 코드 앞에서 죽었다 — 「스텁에 progress 손잡이를 단다」는 성립하지 않는다

`services/ai-api/app/investigation/workflow.py:341`(실물):

```python
progress_seq = 0
ctx.emitter.step_progress(
    "synthesize", "preliminary", progress_seq,
    preliminary={"ranking": [c.failureModeId for c in candidates], "axis": "deterministic"},
)
```

이 줄은 **게이트웨이를 부르기 «전»에 ai-api 가 스스로** 낸다(주석: 「지연 0 이어야 선표시다」).
hold 스텁은 `POST /synthesize` 자리에 서므로 **그 이벤트는 스텁을 지나가지 않는다** — 손잡이를 달아도 붙잡을 것이 없다.

**그래서 붙잡는 자리를 옮겼다: 관측자 쪽 경계.** 브라우저가 받는 run WS(`/api/ws/runs/{runId}` · `lib/contract.ts:70`)에서
`type="step.progress"` 이고 `payload.kind="preliminary"` 인 프레임만 떨어뜨린다(`page.routeWebSocket`).
🔴 이것은 **그물의 무대 장치**이지 화면의 사실이 아니다 — 그래서 기본은 꺼져 있고(`FKT_DROP_PRELIMINARY=1`),
켠 실행에서는 **떨어뜨린 프레임 수**를 자극 실재 칸으로 함께 판정한다(0 이면 무대 부재).

| 실행 | 손잡이 | cold 표본(선표시 0) | warm 표본(선표시 ≥1) | 떨어뜨림 | 결과 |
|---|---|---|---|---|---|
| 14:47:37 | **ON** | **164** | 0 | 1건 | PASS |
| 14:47:5x | OFF(기본) | 0 | 164 | — | PASS |
| 14:48:34 | **ON** | **166** | 0 | 1건 | PASS |

→ **cold 열이 선다(표본 ≥1 · 판정력 있음).** 단 **두 방향은 한 실행에 함께 서지 않는다** —
선표시를 떨어뜨리면 warm 이 0 이 되고, 흘리면 cold 가 0 이 된다. 그래서 **두 실행이 한 벌**이다.

**교정(검출력)**: 손잡이 ON 상태에서 cold 규칙을 **뒤집으면**(`skeleton === 0`) → **FAIL**(표본 165개).
즉 cold 초록은 **165개 표본이 실제로 규칙을 지켰다**는 말이고, 빈 열의 공짜 초록이 아니다.
**손잡이 OFF 교정**: cold 표본이 **0 으로 되돌아간다** — 이 열을 세우는 것이 그 손잡이임을 그 자리에서 보인다.

## 3. 설계 2 (포화) — 🔴 진범은 hold 가 아니라 «세션 수»였다

**먼저 앞판이 왜 못 세웠는지부터.** 같은 세션으로 같은 시나리오를 다시 쏘면 서버는 **같은 run 을 돌려준다**:

```
shot1..shot5 → 200, 전부 runId = RUN-2385c6207b73   (:8850 직접 실측 14:50:27)
```

앞판은 5발을 **동시**에 쐈지만 그 5발은 **한 개의 run** 이었다 — 슬롯이 찰 리가 없다.
내가 「거절이 날 때까지 순서대로」로 바꿔 8발을 쏴도 여전히 503 이 안 났다(같은 이유).

**고친 설계**: 매 발마다 `POST /api/sessions` 로 **새 세션**을 만들어 쏜다.
근거는 설정 실물 — `settings.py:67` `live_concurrency = 1` · `live_queue_max = 2`.
즉 **1(실행) + 2(대기) = 3 이 차면 4번째가 503** 이어야 한다.

| 실행 | hold 스텁 | 포화 자취 | 결과 |
|---|---|---|---|
| 14:50:5x ①② | 켜짐 | (2발째 503 — 잔여 점유가 남아 있던 창) | PASS · PASS |
| 14:51:39 | **꺼짐** | **200,200,200,503**(4발째) | PASS |
| 14:51:5x ×3 | **꺼짐** | **200,200,200,503** (3회 동일) | PASS ×3 |

→ **결정적이다.** 그리고 **hold 스텁이 없어도 선다** — 발주가 전제한 「스텁이 붙잡아야 포화가 된다」는 **틀렸다**.
결정적 축의 조사는 ~200ms 를 사는데 4발이 그 안에 다 들어가므로, 슬롯·큐가 채워진다.
🔴 **이 초록이 막는 것**: 「용량 거절이 code 로 분기한다」가 깨지면 빨강이 난다. 그리고 이제 그 빨강·초록은
**직전 실행의 잔여가 아니라 그물 자신이 만든 조건**에서 나온다 — 같은 명령이 4회 연속 같은 자취(200,200,200,503)를 냈다.

## 5. 내 계측기 자수

1. **발주의 전제를 그대로 구현했으면 「스텁에 손잡이를 달았는데 아무것도 안 잡힌다」로 끝났다.** 코드 실물을 먼저 읽어 그 자리가 아님을 확인하고 경계를 옮겼다 — **발주문도 전언이다**.
2. **ⓒ 의 첫 두 초록(14:50:5x)은 자취가 「2발째」였다.** 잔여 점유가 남아 있던 창이라 **그물이 만든 포화라고 부를 수 없었다** — 스텁을 내리고 4회 반복해 같은 자취가 나온 뒤에야 「결정적」이라고 적었다.
3. **한 실행에서 두 방향을 동시에 세우지 못한다.** cold 초록과 warm 초록은 **다른 실행의 값**이다. 한 줄로 「양방향 통과」라고 적으면 없는 사실이 된다.
4. 이 창 끝에서 **hold 스텁을 내린 채로 뒀다**(교정 B 때문). 무대를 다시 쓰려면 `node tests/web/_synthesis_hold_server.mjs 8858` 부터 세워야 한다.
