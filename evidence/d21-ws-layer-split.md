# D-21 층 분리 — 공개 셸의 WS 미개통은 **어느 층**인가

## §1 왜 앞선 창에서 못 갈랐나 (자수의 연장)

26대의 1차 프로브 2본은 **무쿠키**였다. `session_guard.py:243` 이 **핸드셰이크 단계**에서
무세션을 거절하므로, 그 non-101 은 「가드가 제대로 막았다」와 구분되지 않는다.
⇒ 층 판정에 쓸 수 없어 **부수 관측으로 강등**했고, 이 문서가 그 빚을 갚는다.

**이번에 바꾼 것은 하나** — 두 열 모두 **유효 세션 쿠키 + 같은 실제 run**을 쥐고 물었다.

---

## §2 측정 (E1)

세션·run 은 **계약 경로 그대로** 만들었다: 공개 셸 `/` 입장 → `fkt_sid` 발급 →
`POST /api/scenarios/GS-01/runs`(본문 `sessionId` = 쿠키 값 · v0.1.6 판정 회피) → **status 200 · runId 확보**.

| 열 | 경로 | 쿠키 | opened(101) | 종료 | 소요 |
|---|---|---|---|---|---|
| **A** | Vercel 경유 `wss://<공개셸>/api/ws/runs/<run>` | 있음(그 컨텍스트가 발급받은 것) | 🔴 **false** | `error`(non-101) | 404ms |
| **B** | **Funnel 직결** `wss://<tailnet-host>:8443/api/ws/runs/<같은 run>` | 있음(같은 `fkt_sid` 를 그 오리진에 얹음) | ✅ **true** | `close 1005`(내가 첫 메시지 뒤 닫음) | 39ms |

열 B 의 사전 도달 확인: 같은 오리진 `GET /api/health` → **200**.

🔴 **`1005` 를 실패로 읽지 마라** — 「상태 코드 없이 닫힘」이고, **내 클라이언트가** 첫 메시지를 받은 뒤
`ws.close()` 를 부른 결과다. 판정에 쓰는 값은 **`opened`(101 성립)** 이다.

---

## §3 판정 — **층 = Vercel rewrite 쪽**

발주가 정한 판정선 그대로: 「Funnel 직결이 101 이면 층 = Vercel rewrite / 직결도 non-101 이면 층 = 서버·Funnel」.

- 열 B 가 **101 을 받았다** ⇒ **ai-api 의 WS 라우트도, serve/Funnel 핸들러도, 세션 가드도 살아 있다.**
  (같은 쿠키·같은 run 으로 열렸으니 가드가 통과시킨 것이기도 하다 — 세션 축의 부수 초록.)
- 같은 순간 열 A 는 **101 을 못 받았다** ⇒ 갈린 자리는 **Vercel 엣지 rewrite 구간**이다.
  D-11 이 남겨 둔 「WS 만 rewrite 잔존 · 효과 미측」 칸에 값이 들어간다.

### 3-1. 🔴 이 판정의 사정거리 (넘겨 읽지 말 것)

- 열 B 는 이 노트북에서 **tailnet self 로 붙는다**(39ms · t4-3 계보). 그래서 B 가 시험한 것은
  **「serve 핸들러 + ai-api 층이 101 을 주는가」**이지 **「공개 릴레이를 지난 WS」가 아니다.**
  즉 「Funnel 을 통한 외부 WS 가 된다」는 **이 표로 주장되지 않는다.**
- 그래도 층 판정은 선다: **A 가 죽은 자리에서 B 는 살았다.** 두 열의 차이는 **Vercel 구간**이다.
- 「Vercel 이 WS upgrade 를 rewrite 로 못 넘긴다」는 **원인 가설(E3)** 이고, 이 문서가 세운 **사실(E1)** 은
  「같은 쿠키·같은 run 으로 A 는 101 을 못 받고 B 는 받았다」까지다.
