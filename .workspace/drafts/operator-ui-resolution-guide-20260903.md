## 1. 뿌리 ① — 투어 상태 모델 (B-3 · A-1 · A-2 · C 를 한 번에)

### 1.1 왜 상태 모델부터인가 (설명)

원문 B-3은 「진행 조건이 코드 세 곳에 흩어짐」을 구조 문제로만 적었습니다. 그런데 A-1(어떻게 넘어가는지 안 알려줌), A-2(끊기와 영구 거부가 같음), C(가둠 경계 미정)는 **전부 「진행·중단·포커스」의 규칙**이고, 이건 상태 모델이 정해지면 자동으로 정해지는 것들입니다. 세 곳에 흩어진 조건을 한 곳에 모으는 것이 목적이 아니라, **모으고 나면 저 세 문제의 답이 표 한 장에 나온다**는 것이 핵심입니다.

### 1.2 투어 전체 상태 (A-2의 답)

```
                 ┌──────────┐
   invite ──────▶│  running │──── complete ────▶ completed
   (초대 카드)     │ (step n) │
                 └────┬─────┘
          Esc/닫기 ─┘   └── 「다시 보지 않기」
              ▼                    ▼
          dismissed            suppressed
        (재개 가능·일시)        (영구·사용자 명시)
```

| 상태 | 뜻 | 저장 | 초대 카드 | `?` 버튼 | 재개 시 |
|---|---|---|---|---|---|
| `never` | 한 번도 안 봄 | — | **보임** | 「투어 시작」 | 1단계 |
| `running` | 진행 중 | 세션 + `lastStep` | 숨김 | 「투어 재개」 | `lastStep` |
| `dismissed` | Esc·✕·바깥 클릭으로 **잠깐 끊음** | 영구 + `lastStep` | **보임**(문구: 「이어서 보기」) | 「투어 재개」 | `lastStep` |
| `suppressed` | 「다시 보지 않기」 **명시 선택** | 영구 | 숨김 | 「투어 시작」 | 1단계 |
| `completed` | 끝까지 봄 | 영구 | 숨김 | 「투어 다시 보기」 | 1단계 |

**핵심 규칙 두 줄**
1. **사용자가 명시적으로 고르지 않은 것은 영구가 아니다.** Esc는 의사 표시가 아니라 탈출 키입니다. 원문의 「잠깐 끊은 분에게 영구히 사라짐」은 이 원칙 위반입니다.
2. **`dismissed`는 단계를 기억한다.** 이어 보기가 1단계부터면 다시 끊습니다.

**기존 데이터 이관:** 이미 저장된 `skipped`는 어느 쪽인지 알 수 없으므로 **보수적으로 `dismissed`(재개 가능)로** 취급합니다. 잘못돼도 「초대 카드가 한 번 더 뜸」이 최악이고, 반대로 `suppressed`로 취급하면 「영구히 못 봄」이 최악이라 비대칭입니다.

**Esc 직후 UX(권고, 의견):** 하단에 5초 토스트 「투어를 잠시 멈췄습니다 — [이어서 보기] [다시 보지 않기]」. 이 토스트가 있으면 `suppressed`로 가는 명시 경로가 생기고, `?` 버튼을 찾을 필요가 없어집니다.

### 1.3 단계 유형과 진행 조건 (A-1 · B-3의 답)

단계를 **두 종류**로 선언합니다. 진행 조건은 단계 정의 안에만 있고, 런타임은 그 정의를 **한 곳에서** 해석합니다.

```ts
type Step =
  | { kind: 'info';
      target?: Selector;             // 없으면 중앙 모달(환영·마무리)
      advance: 'next' }              // 「다음」 버튼으로만
  | { kind: 'interactive';
      target: Selector;              // 반드시 있음
      advance: { on: 'click' | 'change' | 'custom'; of: Selector; timeoutMs?: number };
      allowSkip: boolean };          // true면 「건너뛰기」로도 진행
```

| 유형 | 배경 상호작용 | 포커스 | 넘어가는 법 | 화면 표시 |
|---|---|---|---|---|
| `info` | **차단**(오버레이가 클릭 먹음) | 말풍선 안 순회(소프트 트랩) | 「다음」 | 스포트라이트 + 말풍선 |
| `interactive` | **대상만 허용**(오버레이에 구멍) | **단계 진입 시 대상으로 이동** | 대상 조작 이벤트 **또는** 「건너뛰기」 | 스포트라이트 + 말풍선 + **§1.4 가리킴 표시** |

**A-1 「Tab 9번」의 진짜 해법:** 대상을 가리키는 표시를 붙이는 것도 필요하지만(§1.4), 근본은 **`interactive` 단계에 들어가면 포커스를 대상으로 옮기는 것**입니다. 그러면 Tab 9번이 **0번**이 됩니다. 스크린리더 사용자에게는 말풍선 본문을 먼저 읽고(`aria-describedby`) 포커스를 대상으로 보내는 순서가 맞으므로, 대상에 `aria-describedby="tour-step-body"`를 붙여 대상에 포커스가 가도 안내를 듣게 합니다.

**`allowSkip` 기본값은 `true`(의견):** 대상이 안 눌리는 상황(권한 없음·데이터 없음·A-5 같은 크기 문제)에서 투어 전체가 막히는 것보다 낫습니다. 「직접 눌러야만 넘어감」이 교육 효과가 있다는 주장도 있지만, 처음 오신 분이 멈추는 비용이 더 큽니다.

**B-3 「세 곳」 정리:** 지금 세 곳에 있는 조건을 위 `advance` 필드로 옮기고, 런타임은 `resolveAdvance(step)` 하나가 이벤트 리스너를 붙였다 떼는 구조로. 검증은 「`advance`를 읽는 코드가 리포에 **정확히 한 함수**인가」를 `grep`으로 재면 됩니다.

### 1.4 「어디를 누르라」 가리키기 (A-1 화면 쪽)

`interactive` 단계에는 다음 **세 층**을 모두 씁니다. 하나만으로는 어느 사용자군엔가 안 보입니다.

| 층 | 대상 사용자 | 구현 | 주의 |
|---|---|---|---|
| **① 스포트라이트 링** | 시각 사용자 | 대상 둘레에 2px 링 + `spotlightMargin` | 이미 있음. 단 배경이 밝으면 안 보이므로 링 색은 대비 3:1 이상 |
| **② 펄스 비콘** | 시각·주의 분산 | 대상 모서리에 지름 12px 원, 1.5초 주기 확대 | `prefers-reduced-motion: reduce`면 **정적 점**으로. 비콘도 대상 안에 두면 클릭이 대상에 가지 않으니 `pointer-events: none` |
| **③ 말풍선 문구 + 포커스 이동** | 키보드·스크린리더 | 「**{대상 이름}**을(를) 누르세요」로 문구에 대상 이름을 넣고, 진입 시 포커스를 대상으로 | 「직접 눌러 보세요」처럼 **대상 이름 없는 문구는 금지**. 이름은 대상의 접근 가능한 이름(`aria-label`/텍스트)에서 가져와 문구와 화면이 어긋나지 않게 |

**측정(A-1 발견 경위에 대한 답):** 원문이 정확히 짚었듯 그물이 대상을 미리 알면 무의미합니다. 사람에게 유리하게 재는 법:

- **키보드:** 단계 진입 후 **Tab 0회**에서 `document.activeElement === target`. (지금은 9회)
- **마우스:** 검증 코드가 `data-tour-target`을 **쓰지 못하게 하고**, 「스포트라이트 링 안에 있으면서 `pointer-events`가 살아 있는 요소」를 화면 좌표로 찾아 클릭. 이것이 사람이 하는 일과 같습니다.
- **문구:** 말풍선 텍스트에 대상의 접근 가능한 이름이 **부분 문자열로 포함**되는가.

### 1.5 포커스 가둠 경계 — 규격 문장 초안 (C의 답)

원문의 결론 「가두지 않는다」에 **동의하되, 단계 유형별로 나눕니다.** 「전부 안 가둠」이면 `info` 단계에서 Tab이 배경으로 새어 나가 스크린리더 사용자가 길을 잃고, 「전부 가둠」이면 원문 말대로 `interactive` 단계에서 갇힙니다.

> **[규격 초안 — 포커스 경계]**
> 1. `info` 단계에서 Tab/Shift+Tab은 **말풍선 내부 요소를 순회**하고 말풍선 밖으로 나가지 않는다. 배경은 `inert`로 둔다.
> 2. `interactive` 단계에서 순회 범위는 **말풍선 내부 요소 + 대상 요소(및 대상의 자손)** 이다. 그 밖으로는 나가지 않는다. 대상 외 배경은 `inert`로 둔다.
> 3. 단계 진입 시 초기 포커스는 `info`면 말풍선의 첫 버튼, `interactive`면 대상 요소다.
> 4. Esc는 모든 단계에서 투어를 `dismissed`로 만들고 포커스를 **투어를 시작한 요소**로 되돌린다.
> 5. 위 1·2는 「가둠」이 아니라 **「순회 범위 정의」**로 부른다. 범위 밖 요소는 `inert`이므로 「막는다」가 아니라 「존재하지 않는다」에 가깝다.

이렇게 쓰면 검증이 잴 수 있습니다: 「Tab N회 후 activeElement가 범위 집합에 속하는가」. 참고 가이드 §3.1은 `aria-modal="true"`를 권했는데, **`interactive` 단계에서는 `aria-modal`을 붙이지 않습니다**(대상이 다이얼로그 밖에 있으므로 스크린리더가 대상을 못 보게 됨). `info`만 `aria-modal`. 이것으로 참고 가이드를 갱신합니다.

**수용 기준(①)**
- [ ] `advance`를 해석하는 함수가 리포에 정확히 1개
- [ ] `interactive` 단계 진입 후 Tab 0회에 대상이 포커스
- [ ] Esc 후 저장 상태가 `dismissed`이고 `lastStep`이 남음. 초대 카드 「이어서 보기」 노출
- [ ] 「다시 보지 않기」 후에만 `suppressed`
- [ ] 각 단계에서 Tab 10회 동안 activeElement가 규격 §1.5의 범위 집합을 벗어나지 않음
- [ ] 말풍선 문구에 대상의 접근 가능한 이름이 포함

## 2. 뿌리 ② — 배치 재계산 (A-3)

참고 가이드 §4에 알고리즘을 적었으므로 여기서는 **원문이 새로 밝힌 원인 「정착 뒤 값이 바뀌어도 다시 계산하지 않음」**만 다룹니다.

### 2.1 언제 다시 계산해야 하나

| 트리거 | 감지 방법 | 왜 놓치기 쉬운가 |
|---|---|---|
| 대상 크기·위치 변경 | `ResizeObserver(target)` | 데이터 로딩 후 카드가 늘어남 — **첫 화면 76자의 원인이 이것일 가능성 높음**(KPI 수치가 나중에 들어옴) |
| 대상 내용 변경 | `MutationObserver(target, {childList, subtree, characterData})` | 크기는 같은데 글자가 바뀜 |
| 스크롤 | `scroll` (passive, rAF 스로틀) | 스포트라이트는 따라가는데 말풍선은 안 따라감 |
| 뷰포트 변경 | `resize` · `visualViewport.resize` | 모바일 키보드 올라옴 |
| 말풍선 자체 크기 변경 | `ResizeObserver(bubble)` | 문구가 길어져 높이가 늘면 가림 면적이 늘어남 |
| 글꼴 확대 토글(T7-1) | 설정 변경 이벤트 | 어제 만든 기능이 오늘 문제와 결합 |

**구현 원칙:** 트리거를 하나로 모아 `schedulePlacement()`를 호출하고, 이 함수는 rAF 한 프레임 안에서 **한 번만** 실제 계산을 합니다(디바운스). 「정착」을 시간으로 기다리지 말고(200ms 같은 값은 늘 틀립니다) **관찰자로 기다립니다.**

### 2.2 「오른쪽에 붙은 대상은 비킬 자리가 없다」 — 6단계 남은 것

원문의 판단(범위를 그렇게 정한 결과)에 동의합니다. 다만 두 가지는 범위를 안 넓혀도 됩니다.

- **말풍선을 대상 「위」가 아니라 「대상이 가리지 않는 영역 위」에 둡니다.** 대상이 오른쪽 끝에 있으면 좌측 여백은 없어도 대상 **아래·위**로 밀어 넣는 shift가 가능한 경우가 많습니다. 참고 가이드 §4.2의 4번(shift)이 구현돼 있는지 확인.
- 그래도 안 되면 참고 가이드 §4.2의 5번 **fallback(화면 하단 중앙 고정, 화살표 없음)**. 6단계 중 몇 개가 이 모드로 가는지 세어서 **「가림 0자 · fallback n단계」**로 보고하면 됩니다. 「가림 451자」보다 「fallback 3단계」가 더 정직한 지표입니다.

### 2.3 측정 무대

원문의 「측정 무대를 다시 세우는 중」에 대해: 참고 가이드 §3.3의 `overlapRatio` 테스트에 **「데이터 로딩 완료 후 500ms 대기 → 재측정」**을 넣으면 정착 후 회귀를 잡습니다. 단, 그 500ms는 테스트 쪽 대기이지 제품 코드의 대기가 아닙니다.

**수용 기준(②)**
- [ ] 대상에 데이터가 늦게 들어오는 케이스(1단계)에서 로딩 완료 후 가림 0자
- [ ] 6단계 × 3뷰포트에서 가림 면적 < 대상 면적 10% **또는** fallback 모드로 전환됨
- [ ] 글꼴 확대 켬/끔 전환 시 재배치됨

## 3. 뿌리 ③ — 크기·간격 기준 (A-5 · B-1 · B-2)

### 3.1 기준을 두 단으로 (A-5 설명)

원문은 44px 하나로 재고 있어서 「40px 리듬에 44가 안 들어감 → 넓히니 아래 링크가 대신 눌림」의 진퇴양난에 빠졌습니다. **WCAG 2.2는 두 단**입니다.

| 기준 | 수준 | 요구 | 간격 예외 |
|---|---|---|---|
| **2.5.8 Target Size (Minimum)** | **AA** | 24×24 CSS px | **있음** — 대상 중심에 지름 24px 원을 그렸을 때 다른 대상이나 다른 대상의 원과 겹치지 않으면 통과 |
| 2.5.5 Target Size (Enhanced) | AAA | 44×44 | 없음 |

즉 **44는 목표, 24+간격이 합격선**입니다. 왼쪽 메뉴가 40px 높이에 간격 8px이면: 원 지름 24 ≤ 40이고 인접 대상과 원이 겹치지 않으므로 **2.5.8 통과**입니다. 지금 진행 중인 「간격 4→8」은 옳은 방향이고, 44를 억지로 넣어 아래 링크를 먹는 것보다 낫습니다. 보고 문구를 「44 성립」이 아니라 **「AA(2.5.8) 전건 통과 · AAA(44) n/m」**으로 바꾸면 정직하고 남는 문제도 보입니다.

### 3.2 「가로만 남은」 ✕(10.6px)·「다시 보기」(32px) — 히트 영역 확장

**보이는 크기와 눌리는 크기는 다릅니다.** 글리프는 그대로 두고 **눌리는 영역만** 키웁니다.

```css
/* 방법 1: 패딩으로 — 레이아웃에 영향 */
.tour-close { padding: 16px; margin: -16px; }   /* 10.6 + 32 ≈ 43 */

/* 방법 2: 가상 요소로 — 레이아웃 무영향, 인접 요소와 겹치면 안 됨 */
.tour-close { position: relative; }
.tour-close::before {
  content: ''; position: absolute; inset: -16px;  /* 사방 16px 확장 */
}
```

「다시 보기」가 32px인 이유는 아마 **텍스트 링크(`<a>` 또는 `<span>`)**여서일 겁니다. `<button>`으로 바꾸고 `min-width: 44px; padding: 0 12px`. 텍스트 링크는 2.5.8의 「인라인 예외」에 해당해 합격은 하지만, 이건 문장 속 링크가 아니라 **동작 버튼**이므로 예외에 기대지 말고 키우는 게 맞습니다.

### 3.3 16px에서 이미 잘린 글자 17건 (B-1)

원문이 「시안 영역」이라 한 것은 맞지만, **시안 없이 코드만으로 닫히는 부분**과 **시안이 필요한 부분**을 가릅니다.

| 대상 | 원인 | 코드만으로 되는 것 | 시안 필요 |
|---|---|---|---|
| 설비 카드 이름 4건 (`CNC 204호기`) | 카드 폭 고정 + `white-space: nowrap` | `overflow-wrap: anywhere` + **한국어는 `word-break: keep-all`**(어절 단위 줄바꿈) + 카드 높이를 2줄 허용 | 카드 높이가 늘어도 그리드가 무너지지 않는지 |
| ID 줄 12건 | ID가 길고 고정폭 | **중간 생략**(`ABC12…789` — 앞 4 + 뒤 4). CSS만으로는 안 되고 JS로 문자열 생성. 전체 값은 `title`과 클릭 시 복사 | 앞뒤 몇 자를 남길지(ID 체계에 따라 뒤가 식별자일 수 있음) |
| 공통 | 잘림을 아무도 모름 | `element.scrollWidth > element.clientWidth`로 **잘림 감지 → 자동으로 `title` 부여** | — |

**「글꼴 확대와 무관한 별개 병」이 맞습니다.** 그러나 글꼴 확대(1.5배)를 켜면 17건이 **훨씬 늘어납니다.** T7-1이 「Δ 0」인 건 레이아웃 정렬이고 잘림은 재지 않았을 겁니다. 잘림 감지 스크립트를 T7-1 회귀에 넣으면 두 문제를 하나의 지표로 봅니다.

### 3.4 아이콘 색·가짜 버튼 (B-2)

작은 두 건이라 규모(8자리)만 적습니다.

- **아이콘 선 색:** SVG `stroke="#333"` 같은 하드코딩을 **`stroke="currentColor"`**로. 그러면 부모의 `color`(팔레트 토큰)를 따라가고 다크 모드·고대비도 같이 해결됩니다. 8자리 전부 같은 한 줄 수정.
- **버튼처럼 보이는 `<span>` 3자리:** `<button type="button">`으로 교체가 정답. 교체가 어려우면 최소한 `role="button" tabindex="0"` + Enter/Space 키 핸들러. 후자는 **세 가지를 다 해야** 하고 하나라도 빠지면 `<span>`보다 나쁩니다(스크린리더는 버튼이라 하는데 키보드로 안 눌림).

**수용 기준(③)**
- [ ] 모든 인터랙티브 요소가 2.5.8(24px 또는 간격 예외) 통과 — 자동 측정 가능
- [ ] ✕·「다시 보기」 히트 영역 ≥ 44×44
- [ ] 16px·24px(1.5배) 두 설정 모두에서 `scrollWidth > clientWidth`인 텍스트 요소 0건 **또는** `title` 부여됨
- [ ] `stroke`/`fill`에 hex 하드코딩 0건 (`grep`)
- [ ] `role="button"` 인 `span` 0건 또는 키 핸들러 동반

## 4. A-4 「미연결」 — 5초 처방의 한계

참고 가이드 §5와 같은 항목입니다. 원문이 「첫 호출만 5초, 이후 2초」로 구현 중이라 **그 처방에 대한 의견**만 보탭니다.

- **5초는 증상 대응입니다.** 콜드 1.83초는 오늘 값이고, 함수 크기·리전·의존성이 바뀌면 3초가 됩니다. 5초도 언젠가 뚫립니다.
- **판정을 3상태로 바꾸는 것이 근본입니다:** `checking → (응답) connected | (타임아웃) retrying → (2회 실패) disconnected`. 그러면 상한이 2초든 5초든 **사용자가 「미연결」을 보려면 3번 연속 실패**해야 합니다.
- **첫 화면에 「미연결」이 뜨는 것 자체를 막는 두 번째 방어:** 상태 배지의 초기 렌더를 「확인 중」(회색·스피너)으로. 지금은 초기값이 「미연결」이거나 타임아웃이 곧바로 「미연결」을 그리는 구조로 보입니다.
- **투어와의 결합:** §1.3에서 1단계를 `info`(대상 없음·환영)로 두면 「첫 단계가 미연결 배지를 스포트라이트」하는 최악 조합이 사라집니다.

**수용 기준:** 서버를 강제로 식힌 뒤(배포 직후 또는 15분 유휴) 첫 열람에서 「미연결」이 **한 프레임도** 그려지지 않음 — 스크린샷 연속 촬영으로 측정.

## 5. 뿌리 ④ — 사람보다 유리한 측정 (D-1 · D-2 · D-3)

이 절은 폐하께서 직접 하실 30분 절차입니다. **순서대로 하면 30분**이고, 결과를 한 파일에 적어 주시면 좌석이 처방합니다.

### 5.1 D-1 실제 기기 터치 — 10분

준비: 폰(한 대면 됨), 공개면 URL.

| # | 할 것 | 적을 것 |
|---|---|---|
| 1 | 왼쪽 메뉴 3개를 **위에서부터 차례로** 한 번씩 누름 | 의도한 것이 열렸나 / **아래 것이 열렸나** |
| 2 | 같은 메뉴를 **엄지 옆면**으로(정확히 안 누르는 흉내) | 위와 같음 |
| 3 | 투어 시작 → 말풍선의 ✕ 누름 | 한 번에 닫혔나 / 몇 번 시도했나 |
| 4 | 초대 카드의 「다시 보기」 | 위와 같음 |
| 5 | 투어 `interactive` 단계에서 **말풍선이 가리키는 것**을 누름 (문구 안 읽고 화면만 보고) | 무엇을 눌러야 할지 **바로** 알았나 |
| 6 | 폰을 가로로 돌림 | 말풍선이 화면 밖으로 나갔나 |

에뮬레이션이 못 재는 것은 **손가락 폭(16~20mm)과 의도 어긋남**입니다. 2번이 그걸 흉내 냅니다.

### 5.2 D-2 스크린리더 — 15분

준비: Windows **내레이터**(Win+Ctrl+Enter). 또는 macOS VoiceOver(Cmd+F5). 브라우저는 Edge/Chrome.

| # | 할 것 | 정상 | 이상(적어 주세요) |
|---|---|---|---|
| 1 | 투어 시작 버튼에 도달 | 「투어 시작, 버튼」 | 이름이 없거나 다름 |
| 2 | Enter | 「대화상자, {1단계 제목}」 후 본문 | 제목 없이 본문만 / 아무 말 없음 |
| 3 | Tab 3~4회 | 다음·이전·닫기 버튼 이름이 차례로 | 배경 요소(메뉴·카드)가 읽힘 → **범위 이탈** |
| 4 | 「다음」 Enter | 「2/9단계, {제목}」 **한 번** | 🔴 **두 번 읽힘**(원문이 걱정한 이중 읽기) / 안 읽힘 |
| 5 | `interactive` 단계 진입 | 「{대상 이름}, 버튼, {안내 문구}」 | 대상으로 안 감 / 안내 없이 버튼 이름만 |
| 6 | Esc | 「투어 시작, 버튼」(포커스 복귀) | 다른 곳으로 감 / 아무 말 없음 |

**이중 읽기 원인과 처방(미리 적어 둡니다):** 단계 이동 시 ① `aria-live` 영역에 「2/9단계 …」를 넣고 ② 동시에 포커스를 새 말풍선(또는 대상)으로 옮기면, 스크린리더가 **live 영역 + 포커스 이동 두 번** 읽습니다. 처방은 **둘 중 하나만**: 포커스가 이동하는 구조면 live 영역을 **비우고**, 말풍선의 `aria-labelledby`에 「2/9단계 · 제목」을 포함시켜 포커스 이동 한 번으로 다 읽히게 합니다. live는 포커스가 안 움직이는 갱신(예: 「건너뛰었습니다」)에만 씁니다.

### 5.3 D-3 실사용자 5분 — 5분

**규칙 하나:** 좌석의 설명을 듣지 않고, 문서를 읽지 않고, **폰이 아니라 PC로**, 처음 보는 사람처럼 엽니다.

1. 첫 화면을 5초 봄 → **「이 화면이 뭘 하는 화면인지」 한 문장**으로 적음. (좌석이 의도한 문장과 다르면 그게 첫 문제)
2. 투어를 **안 읽고** 「다음」만 연타 → 어디서 막혔나
3. 투어를 **읽으면서** → 「이건 왜 있지?」 싶은 단계 번호
4. 투어를 끊고(Esc) 다시 찾으려 해 봄 → **몇 초 걸렸나** (A-2 측정)
5. 알람 하나 눌러서 원인 후보까지 감 → 막힌 곳

적을 것은 **「막힌 곳·헷갈린 곳·예상과 다른 곳」 세 종류만**. 잘된 것은 안 적어도 됩니다.

## 6. 검증 그물 자체를 고치기 (④의 근본)

원문 A-1의 발견 경위 — 「그물이 대상을 미리 알고 있었다」 — 는 이번 한 건이 아니라 **검증 설계의 결함**입니다. 세 가지 규칙을 검증 규격에 넣기를 권합니다.

1. **블랙박스 규칙:** E2E 검증은 `data-tour-*` 같은 **테스트용 속성을 셀렉터로 쓰지 않는다.** 접근 가능한 이름(`getByRole`, `getByLabel`)과 **화면 좌표**로만 찾는다. 사람이 쓰는 것과 같은 정보만 쓴다.
2. **비용 측정 규칙:** 「완주 PASS」만 내지 말고 **비용을 같이 낸다** — Tab 횟수, 클릭 횟수, 단계별 체류 시간. 「9단계 완주, Tab 총 31회」였다면 A-1은 발견됐을 겁니다.
3. **자기 신고 규칙(이미 있음):** 좌석이 「그물이 유리했다」고 신고한 것은 훌륭합니다. 이걸 **검증 보고서 고정 항목** 「이 측정이 사람보다 유리한 점」으로 만들어 매번 쓰게 합니다. 빈칸이면 통과가 아니라 미기재.
