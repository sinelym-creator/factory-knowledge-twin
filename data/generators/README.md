# synthetic seed 생성기 (T1-2)

GS-01이 실제로 도는 합성 구조 데이터를 **손으로 만든 데이터가 아니라 재실행 가능한 코드**로 만든다.
CSV는 산출물이고 이 디렉터리의 코드가 정본이다 — `data/generated/`는 커밋하지 않는다.

## 1명령

```powershell
pwsh data/seed.ps1                 # 생성 → 적재 → 검증
pwsh data/seed.ps1 -SkipGenerate   # 이미 만든 CSV로 적재만
pwsh data/seed.ps1 -SkipLoad       # 생성만 (DB 없이 멱등 확인)
```

전제: compose 스택 기동 + `pwsh services/ai-api/db/migrate.ps1` 적용 완료.
좌석별 병렬 스택은 `docs/product/dev-environment.md` §4.2를 따른다.

## 멱등 — 두 축이 함께 성립한다

| 축 | 방법 | 실측 |
|---|---|---|
| 생성 | `RANDOM_SEED` 고정 + **기준 시각 고정**(`REFERENCE_NOW = 2026-08-26T14:30+09:00`) | `data/generated/manifest.sha256` 두 벌 diff |
| 적재 | seed 테이블 24종 `TRUNCATE` 후 재적재 | 2회 연속 적재 오류 0 |

🔴 **`datetime.now()`를 부르지 않는다.** 시각을 실행 시점에서 가져오면 재실행마다 데이터가
달라져 「생성 2회 diff 0」이 원천적으로 불가능하다. 기준 시각은 GS-01 알람 ID
(`AL-20260826-0041`)의 날짜와 정합하도록 못박았고, 모든 날짜는 그 값의 상대 계산이다.

🔴 **문자열 `hash()`를 쓰지 않는다.** `PYTHONHASHSEED`에 따라 실행마다 값이 달라진다 — `zlib.crc32`를 쓴다.

## 🔴 의도적 불완전성 — 이건 버그가 아니라 요구다

평가 40문항(`benchmarks/datasets/eval-questions-draft.md`) 중 2문항은 **데이터가 불완전해야만**
성립한다. 데이터를 «너무 완전하게» 만들면 문항이 조용히 무력화된다.

| # | 요구 | 구현 | 연결 문항 |
|---|---|---|---|
| **D-2** | `DOC-SOP-0014`의 두 revision이 **값이 실제로 다를 것** | `@r1` = 공구 4종·90분·LOTO만 / `@r2` = 공구 5종(고온 그리스·교정 토크렌치)·120분·LOTO+PPE. 본문 sha256도 다르다 | `Q-DIRECT-003` — 「이전 revision과 무엇이 다른가」에 쓸 정답이 필요하다 |
| **D-5** | SOP가 **매핑되지 않은** 고장모드 1건 | `FM-TOOL-IMB` 하나만 `failure_mode_sop`에 넣지 않는다. 그리고 R09(설비 직결)로 `EQ-CNC-204`에 붙인다 | `Q-MULTIHOP-003` — 부품 경유(R08)만 훑으면 이 모드를 **아예 보지 못하고** 「전부 매핑됨」이라 오답한다 |

같은 이유로 **함께 지킨 것들**:

- **D-3** SOP 본문에 절 구조를 둔다(`§4 필요 공구 및 자재` · `§5 예상 작업 시간`) — `Q-DIRECT-002`의 채점 기준.
- **D-6** PPE 안전 규정 ID를 `SAF-PPE-01`로 확정 — `Q-SAFETY-001`이 「안전 규정 전량」을 요구한다.
- **D-8** `MR-2025-0087` → `WO-2025-0087` → `INC-2025-019` 연결 — `Q-MULTIHOP-002`. (§ 미결 1 참조)
- **Q-UNANS-001** 어떤 문서 본문·note에도 **원가·단가·금액을 쓰지 않는다**. 비용이 데이터 어디에도 없어야 「근거 없음」이 정답이 된다.
- **Q-UNANS-002** `EQ-CNC-999`를 **생성하지 않는다**. 자기 점검이 전 테이블을 훑어 출현을 막는다.
- **정답 누설 방지** 진행 중인 `INC-2026-014`에는 `incident_diagnosis`를 넣지 않는다. 정답(FM-BRG-WEAR)을 미리 넣으면 GS-01 S6에서 에이전트가 추론하지 않고 읽어 버린다. 진단은 **종결된** incident에만 있다.

## 데이터 정합에서 특히 신경 쓴 것

- **알람 25건 전량이 시계열과 맞는다.** 정상 파형은 임계를 넘지 않으므로, 알람만 만들면
  「알람은 있는데 그 시각 계측값은 임계 미만」인 모순이 남는다. 알람 계획을 먼저 세우고
  파형에 스파이크를 주입한 뒤, `observed_value`를 **주입된 파형에서 다시 읽어** 채운다.
- **GS-01 알람의 발생 시각을 하드코딩하지 않는다.** 이상 파형이 경보 임계를 처음 넘은
  격자점을 스트리밍 중에 잡아 `raised_at`으로 쓴다. 파형을 손보면 알람도 따라 움직인다.
- **설비 일련번호는 12대 전역에서 유일하다.** `SN-{EQ_NUM}-{MEAS}` · `CP-{EQ_NUM}-{CLASS}-{NN}`이
  설비 번호를 품기 때문에, 라인마다 번호를 재사용하면 PK가 충돌한다.

🔴 **SensorReading 720행 차이는 추정치의 누락분이다.** §5는 기저(30센서 × 1분 × 21일 =
907,200)와 사건 구간(3센서 × 1초 × 4시간 = 43,200)을 단순 합산했는데, 두 구간이 겹치는
3센서 × 240분 = **720행이 PK(sensor_id, ts) 중복**이다. 생성기는 사건 구간의 1분 데이터를
빼고 1초 데이터로 대체한다. 스펙 결함이 아니라 **실측으로 갱신할 추정치**다(E4 → E1).

## 범위 — 여기서 만들지 않는 것

- **DocumentChunk·embedding = T1-4(색인)** 소관이다. chunk 크기 정책(400~600 token)이 아직
  미결이고(`data-ontology-spec.md` §8 Q2), `eval-questions-draft.md` §0.6이 「chunk_id는
  **색인 빌드 이후** 바인딩한다 · 색인 전 확정 기재는 그 자체로 stale 근거가 된다」로 순서를
  못박았다. 대신 `document_revision.body`에 **원문 전량**을 넣어 T1-4가 청킹할 원천을 남겼다.
- **Neo4j 그래프 투영 = T1-5** 소관. 본 생성기는 PostgreSQL만 채운다.

## 미결 — 판정 필요

1. **D-8의 기대 답 좌표.** `eval-questions-draft.md` §5 D-8은 「`MR-2025-0087`·`WO-2026-0113`·
   `INC-2026-014` 상호 연결」을 요구하는데, `MR-2025-0087`은 **2025년 2월** 이력이고
   `WO-2026-0113`·`INC-2026-014`는 **2026년 8월 현재 사건**이다. 2025년 정비가 2026년
   작업지시서에서 나올 수 없어 그대로 이으면 시간이 역행한다.
   생성기는 **인과 정합**을 택해 `MR-2025-0087 → WO-2025-0087 → INC-2025-019`로 이었다
   (`Q-MULTIHOP-002`의 질문 「그 이력을 **낳은** 작업지시서·Incident」에도 이쪽이 맞다).
   `INC-2026-014`·`WO-2026-0113`과는 공통 고장모드 `FM-BRG-WEAR`로 이어진다.
   → 평가 문항의 `expected_graph_path` 정정이 필요한지 **판정 요청**.
2. **§5 SensorReading 추정치 갱신**(950,400 → 949,680) — `docs/**`는 오케 lane이라 여기서 고치지 않았다.
